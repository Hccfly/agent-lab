# Agent 编排技术调研与演进记录

## 背景

项目最初用少量 Python 手写 Tool Calling、ReAct、Planner–Executor、记忆与 RAG。随着控制流从
单轮工具调用扩展到并行任务、持久恢复和人工介入，继续向一个 while 循环叠加分支会让状态边界、
失败语义和测试成本快速恶化。

因此后续演进遵循一个约束：保留手写实现作为可读的行为基线，只替换编排层；模型、工具和提示词
通过依赖注入保持可替换，使两种实现能在同一组场景下验证。

## 上游项目调研

| 项目 | 重点观察 | 吸收到本项目的设计 | 没有直接照搬的部分 |
|---|---|---|---|
| LangGraph | 显式 State/Node/Edge、checkpoint、interrupt、Send | 单/多 Agent 状态图、SQLite 恢复、HITL、并行 DAG | 高层 `create_agent`，避免遮蔽原有模型和工具边界 |
| OpenHands | Agent、Runtime、Sandbox、Event 的职责边界 | 将执行治理与可观测从业务编排中分离 | 完整沙箱运行时，当前工具面较小且仍是单机进程 |
| browser-use | Observe–Act–Verify、动作失败后的重新观察 | 将工具结果和错误统一回填模型 | 浏览器动作层，暂未引入新的外部执行环境 |
| smolagents | Tool Calling 与 Code Agent 的抽象差异 | 保留多种 Agent 范式作行为对照 | 代码执行 Agent，现阶段不扩大执行权限 |
| CrewAI | Role/Task/Crew 的业务抽象 | 声明式角色注册表和最小工具集 | 隐式协作流程，项目继续使用显式依赖 DAG |
| Dify | 工作流配置、发布、日志和运营界面 | 强化事件、报告和服务接口 | 可视化平台与运营后台，不把编排内核扩成产品平台 |

调研的目的不是按热度替换技术栈，而是识别当前系统真正缺少的机制。这里优先解决状态持久化、
恢复语义、并行合流和观测边界；UI、浏览器自动化和分布式执行留在需求出现之后。

## 演进里程碑

| 阶段 | 改动 | 关键验证 |
|---|---|---|
| 控制流显式化 | 将手写 model/tools 循环映射为 StateGraph | State 可序列化，条件边和终止路径明确 |

| 人工介入 | 敏感工具前动态 interrupt | approve/reject/edit，审批前零副作用 |
| 执行治理 | 路径白名单、原子写、锁、超时、限流 | 路径穿越、并发写、超时与槽位释放测试 |

| 可复现性 | 架构文档与离线验收总入口 | 无网络、无 API Key 环境可重复验证关键路径 |

## 关键实现结论

### 手写循环与状态图

| 手写实现 | LangGraph 实现 |
|---|---|
| `for`/`while` 循环 | `model -> tools -> model` 条件环 |
| 局部变量 `convo` | `AgentState.messages` + 追加 Reducer |
| `message.tool_calls` 判断 | `route_after_model` 条件边 |
| 工具分发循环 | `tools` 节点 |
| 局部去重缓存 | `AgentState.tool_cache` |
| 达到轮次后 return | `force_stop` 显式终止节点 |
| 隐含执行过程 | State 业务轨迹 + 图外运行时 span |

没有使用预构建 ToolNode，是为了保留既有 OpenAI-compatible 消息协议、工具治理和 V1/V2 的可比性。

### 多 Agent DAG

父图路径为 `planner -> scheduler -> Send(executor...) -> scheduler -> summarizer`。Planner 的输出先
验证任务 ID、缺失依赖、自环和多节点环；Scheduler 每个 superstep 传播失败，再计算全部就绪任务。
分支只返回自己的 task_id 增量，Reducer 合并时遇到同 ID 冲突直接报错，避免静默覆盖。

当前采用整波屏障：快任务的后继仍需等待同波慢任务完成。它简化了 checkpoint 边界和故障传播；如果
未来任务规模和尾延迟成为瓶颈，再考虑事件驱动的逐任务放行。

### checkpoint 与副作用

checkpoint 保证从最近成功提交的 superstep 恢复，不自动赋予外部系统 exactly-once。工具副作用完成、
节点结果尚未提交时仍存在崩溃窗口。生产写操作应携带业务幂等键，并依靠数据库唯一约束、事务或外部
服务的幂等接口封闭这个窗口。

### HITL 与节点重进

LangGraph 恢复 interrupt 时会从节点开头重进。因此 interrupt 前只做无副作用的筛选和参数整理，
真实工具调用全部位于 interrupt 返回之后。审批请求和响应保持 JSON 可序列化，才能跨进程持久化。

### 两层轨迹

业务 trace 属于 State，用于验证工具选择、回填、重试和任务状态；RunObserver 位于图外，记录节点
起止、耗时、状态增量和未捕获异常。后者持有锁、时钟和回调，不进入 checkpoint schema。可恢复的
工具错误记为业务 `ok=false`，逃出节点边界的异常才是 `node_error`。

## 评测口径

- 业务通过率同时检查答案与轨迹；模型异常、循环上限和注入故障单列“预期行为”。
- 工具请求与实际执行分开统计，缓存命中只增加请求数。
- 多 Agent 场景按依赖先后校验，允许同层任务乱序。
- usage 任一轮缺失时 Token 记为 null，不从文本长度估算。
- 离线延迟包含 V2 每次建图，不解释为框架纯运行时开销。
- 确定性 Mock 证明控制流和恢复语义，不代表开放问题质量或线上性能。
