# V1 / V2 对比评测

本阶段交付了同题评测器、离线基准结果和独立进程恢复实验。真实 API 模式已经提供，当前提交的
报告只包含离线数据；真实模型成功率、延迟和 Token 成本尚未实测。

## 1. 如何复现

在项目目录的 PowerShell 执行：

```powershell
.venv\Scripts\python.exe -X utf8 eval_compare.py --mode offline --repeats 3
```

默认生成 `reports/offline-eval.json` 和 `reports/offline-eval.md`。JSON 保存每次运行的观测数据、
版本信息、场景快照和源码 SHA256；Markdown 汇总结果。测试执行器不读取 `.env`，阻止 socket
连接与云追踪，FakeClient 不提供 usage，所以 Token 显示 N/A。

以下命令会调用 `.env` 配置的真实 API，并消耗该账号额度：

```powershell
.venv\Scripts\python.exe -X utf8 eval_compare.py --mode live --repeats 3 --output reports/live-eval
```

live 模式运行纯对话、精确计算、三任务 DAG 共 3 个业务场景，不注入人为故障；默认的恢复实验
仍明确是独立离线实验。`--skip-recovery` 可只测业务流程。两种模式的默认输出文件不同。
评测限制工具为计算器与时间查询，真实模型即使意外提出读文件也不会读取本机资料。

运行评测器单测：

```powershell
.venv\Scripts\python.exe -X utf8 tests\test_eval_compare.py
```

## 2. 源码阅读顺序

1. `eval_scenarios.py`：8 个用例与独立预期结果；FakeClient 根据已收到的消息决定下一步。
2. `eval_compare.py / Recorder`：在实际 SDK 请求和工具执行边界观测，不以模型声称的动作代替执行。
3. `run_case()`：V1 在独立评测进程临时替换依赖，退出上下文即恢复；V2 通过 AgentDependencies 注入。
4. `score()`：检查答案、终止状态、工具参数/次数、消息配对与 DAG 依赖先后关系。
5. `summarize()`：计算通过率、调用计数和延迟统计，再生成 JSON/Markdown。
6. `eval_recovery.py`：启动全新的 Python 子进程验证重启恢复，临时库和台账在结束后自动清理。

旧的 `evaluate.py` 保留为原有手写版评测；V1/V2 对比命令是 `eval_compare.py`。

## 3. 场景与评分

| 场景 | 检查点 |
|---|---|
| dialogue | 不请求/执行任何工具，回复预期文本 |
| arithmetic | 调用 calculator(127*53)，答案包含 6731 |
| dedup | 提出两次相同调用，实际只执行一次 |
| tool_retry | 首次工具临时失败，错误回填，再次执行成功 |
| tool_timeout | 注入 ExecutionTimeout，错误回填并恢复；此处不测试真实时间阈值 |
| loop_limit | 三轮后终止，真实时间工具执行三次 |
| model_error | 模型调用抛出指定异常，评测器记下错误并继续其他用例 |
| multi_diamond | 12*5 与 7*8 可乱序并行；60+56 只能在两项成功结束后执行 |

工具超时的线程/信号量行为由治理测试覆盖；对比评测验证 Agent 收到超时异常后的行为。
模型异常场景的通过表示“故障被观测并隔离”，不表示业务回答成功，也不表示 Agent 自动修复了模型。

业务通过率只统计正常业务场景，包含答案与轨迹检查。故障场景计入单独的“预期行为通过率”。
否则把正确处理异常计为失败、或把异常计为业务成功，都会扭曲数据解释。

答案目前使用固定参考值/关键词规则。live 模式的算式参数和调用次数也是严格契约，模型使用另一种
等价算式会被判轨迹不符。因此这是约定用例的回归指标，不是开放题的语义正确率。

## 4. Token 和工具次数如何避免虚高/虚低

模型代理覆盖 V1/V2 的 Planner、Executor 和 Summarizer，所有请求都进入同一计数器。
模型提出的 `tool_calls` 计入 `tool_requests`，进入实际工具执行函数才计入 `tool_executions`，
失败尝试也属于执行。缓存命中时只增加请求次数。

usage 中的 prompt/completion/total 分别累加。任何一轮缺少对应数据，就把整个运行的该指标记为
`null`，同时保存 usage 覆盖率和逐次原始数据。离线 FakeClient 没有真实 Token，不能拿人为数字
当成真实消耗，也不根据 Token 臆测费用。货币成本需要真实 usage 与指定模型计费口径。

## 5. 恢复实验如何保证是新进程

两版使用相同三任务计划，在 task 1/2 完成后退出子进程。父进程检查台账确实只有这两个计算，
然后通过 `subprocess.run()` 启动新解释器。V1 从头调用原流程；V2 通过同一个 thread_id 和
SQLite 调用 `resume()`。台账记录参数、进程 PID 和阶段。

本次结果：V1 最终能完成，但重跑两次已完成工具；V2 最终完成且重复次数为 0。这里的恢复
成功定义为“最终完成且已完成项不重跑”。每版仅测一个中断位置，报告以 0/1 和 1/1 展示，
不能推广成生产恢复成功率 0% 或 100%。

实验模拟已提交波次后的受控退出；工具执行完成、checkpoint 尚未提交之间的崩溃窗口不在此次
实验范围内。后续可以按不同中断位置扩大样本，而不是据此宣称任意副作用 exactly-once。

## 6. 本次结果怎么讲

报告见 [offline-eval.md](../reports/offline-eval.md)，原始数据见
[offline-eval.json](../reports/offline-eval.json)。

本次 8 场景 × 2 版本 × 3 次共 48 次运行均满足预期。每版 3 次重复合计模型请求 69 次，
工具请求 39 次、实际执行 36 次，差异来自缓存去重。V2 本地中位耗时高于 V1；这次把 V2 每次
建图也计入延迟，不能将其直接解读成框架纯运行时开销，更不能推断真实 API 性能。

评测结论摘要：

> 我给手写和 LangGraph 两种编排实现做了共用评测器，区分工具请求和实际执行，按依赖关系
> 检查并行合流，并把业务通过率与故障处理通过率分开统计。离线 48 次运行全部符合预期；
> 独立进程恢复实验中，手写版重跑了两个任务，checkpoint 版没有重跑。离线测试不能反映
> 真实模型成功率和 Token 成本，所以这些指标我保留为待真实 API 评测的数据。
